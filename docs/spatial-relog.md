## What changes and why

The log is meant to help locate access points afterwards, by averaging the positions an access point was
heard from. That works best with several rows per access point per pass: approaching, passing, leaving.
Before this change the device wrote about one row per access point per power-on, because both dedupe tables
(one on each scanner, one on the controller) dropped every repeat of a known access point.

Now an access point is logged again when the device has moved far enough or the signal got clearly stronger
since its last row. For each access point that reaches the SD write step:

1. Not seen before (or evicted from the gate): log it.
2. Seen before without a position, and a position is now available: log it.
3. Both rows have positions and the distance from the last logged position is at least the distance
   threshold: log it.
4. Signal is at least the gain threshold stronger than at the last logged row: log it.
5. Otherwise: suppress it and count it.

Without a GPS fix a network is logged once, as before. When a fix first arrives, networks that were logged
without a position are logged once more with one. Expect roughly 3 to 6 times more rows per drive.

## Defaults and turning it off

On by default in every build from this fork: 25 m and 6 dB. No build flags are needed.

To turn it off, build with:

```
-DRELOG_DISTANCE_M=0 -DRELOG_RSSI_GAIN_DB=0
```

CSV rows are then identical to before. Only the version string and two status-line counters differ.

The version string is `0.2-relog1`. It also appears as `appRelease=0.2-relog1` in the first line of each
CSV.

Both the controller and the scanners must be updated for the full effect. Mixed versions (new controller
with old scanners, or the reverse) log exactly as before; this is verified by simulation tests, so a
partially applied update is never harmful.

## Status-line counters

- `relog`: re-logged rows written (rows for an access point that had already been logged).
- `relog_supp`: repeats suppressed by the gate.
- `dedupe_drop`: now counts repeats inside the 1-second window (the short time-to-live on the dedupe
  tables), not every repeat as before.

## WiGLE compatibility

The CSV format, header and file naming are unchanged. Repeat rows are genuine new observations (new time,
new position or stronger signal), like the repeated observations the WiGLE Android app writes as the device
moves. WiGLE does not formally document this either way; if it ever objects, building with 0/0 restores the
previous behaviour.

## Size impact

| Target | RAM before | RAM after | Flash before | Flash after |
| --- | --- | --- | --- | --- |
| Controller | 130324 | 242908 | 188304 | 190712 |
| Scanner | 152156 | 168172 | 1031989 | 1032225 |

All figures in bytes. The scanner RAM increase of 16016 bytes is the 4000-entry timestamp array added to its
dedupe table. The controller RAM increase of 112584 bytes is the gate entries (80000), the gate slots
(16384), the controller's own timestamp array (16000), and small fields.

## Safe flash procedure

Both chips have ROM recovery that no firmware can overwrite: RP2350 USB BOOTSEL (UF2) and ESP32-C5 USB
download mode (merged image). Scanner updates write to the inactive partition and switch only after the
write succeeds, so a failed scanner update keeps the old image.

1. Get the release images and verify them. Download the workflow artifacts (`controller.bin`,
   `scanner.bin`, the UF2 and the merged scanner image, plus `SHA256SUMS.txt`). Run
   `sha256sum -c SHA256SUMS.txt` in the download folder; every line must say OK.
2. Keep the currently installed release's images (SD and USB variants) as the rollback set. Do not
   overwrite them.
3. Bench first, not on a drive. Copy `controller.bin` and `scanner.bin` to the SD card root, power on with
   stable power, and wait for both to be renamed `controller.applied.bin` and `scanner.applied.bin`.
   Then confirm the controller reports `0.2-relog1` in its USB serial status or boot output, and that the
   controller's scanner OTA output shows success for every scanner.
4. Bench smoke test: a few minutes walking or idling with a GPS fix. Rows are written, `Queue drops` and
   `serial_drop` stay at 0, and a stationary period does not grow the log beyond a few rows per access
   point.
5. Optional test drive on a known route: rows per access point should be about 3 to 6 times higher than on
   the same route with the old firmware, `relog` rises, drops stay at 0, and the `blank_gps` share is
   unchanged.
6. Rollback: copy the previous release's `controller.bin` and `scanner.bin` to the SD root the same way.
   If a board will not boot, recover over USB: BOOTSEL plus UF2 for the controller; ESP32-C5 download mode
   plus the merged image for each scanner.

### How to confirm a scanner update

The scanners do not report a firmware version over SPI. The protocol is deliberately unchanged, so that
mixed versions stay safe. A scanner update is therefore confirmed by three things: the `scanner.applied.bin`
rename, the controller's scanner OTA success output, and `relog` rising on a moving test.
